# The Moolt-Lan_Coop mod as built

A reference for working on the mod: what exists, how a session flows, the sync protocol, and the pitfalls already paid for. Goals, decisions and open work are in [lan-coop-plan.md](lan-coop-plan.md), how to test in [testing.md](testing.md), vanilla internals in [brotato/](brotato/). The step-by-step history is in the git log.

## Session flow
1. **Host / join** (`LanNet.host()` / `join()`): sets `active`, `is_host`/`is_client`, blocks saves (`ProgressData.lan_coop_saves_blocked`), unlocks everything (own unlock lists restored on leave), switches to the solo mouse rule. Client sends `_rpc_hello`; host validates (protocol, game version, DLCs, full, in progress), makes the name unique in the lobby (`NetProtocol.make_unique_name`: " 2", " 3", … appended, any case) and answers `_rpc_welcome(player_index, rejoin_token)` or `_rpc_rejected(reason)` (during a run only a known rejoin token gets in, item 12).
2. **Lobby**: `LanNet.players` (entries from `NetProtocol.new_player_entry`, sorted by `player_index`; the host is peer 1 and index 0; `team` 0/1, by default the index's parity) and `lobby_settings` (`zone`, `difficulty`, `run_id`, `in_wave`, `run_over`, `scaling`, `mode`, `item_sets`) are broadcast with `_rpc_lobby_state` on every change. Clients change their own entry with `_rpc_update_player`.
3. **Start** (`start_run`): host builds the mode (`ModeRegistry.create(lobby_settings.mode)`, a new serial), builds the run (`RunBuilder.build_run`), lets the mode set up its state and change the run (`mode.start(players)`, e.g. endless) and sends the mode state (`_rpc_mode_state`), then serializes the run, applies its own copy from the same JSON, sends `_rpc_run_state(run_id, json, digest)`; clients apply and ack. Any lobby change makes the run stale (`run_id` = 0).
4. **Wave**: once every client acked, the host sets `run_in_progress` (`lobby_settings.in_wave`), fills `CoopService.connected_players` (own device 0, which reads keyboard and first gamepad, its type following the last input; others -1), sends `_rpc_enter_wave(run_id)` and everyone loads `main.tscn`. The `main.gd` extension adds `LanWaveSync` in `_ready`.
5. **Wave end**: unless the wave failed, the host's `main.gd` extension runs `RunData.on_wave_end()` / `LinkedStats.reset()` and `LanNet.send_wave_end_state`: the run after the wave (JSON, applied on the host too) with its digest and each player's pending level-ups and crates (`RunBuilder.pack_pending`: `[[levels], [consumable ids]]` per player) and the wave's lifetime-counter changes (`progress.get_wave_delta()`) go out as `_rpc_wave_end_state(run_id, wave, json, digest, pending, counters)`. A client applies it once its own wave is over (end-wave timer ran, or it left `main.tscn`), takes over the counters (`progress.apply_wave_delta`, then `ChallengeService.lan_check_counted_challenges`), stores `LanNet.wave_end_state = {wave, pending, ok}` and answers `_rpc_wave_end_ack(wave, ok)`. Both roles emit `LanNet.wave_end_ready` once `wave_end_state` is set (`main` relays it as its own `lan_wave_end_ready`, which a client's end-wave code yields on).
6. **Upgrades** (not after a lost or won run): every peer stops `LanWaveSync` (`stop()`: no physics, `LanNet.wave_sync` = null, so late snapshots and events are dropped), enters the solo view (`game/solo_view.gd`) and runs vanilla's solo flow on the solo `UpgradesUI` with its own pending level-ups and crates from `wave_end_state` (`player_index` 0; the own things-to-process icons are rebuilt from them). Before it, main drops `StatsManager`'s pending reloads (`_lan_drop_stats_reloads`): vanilla recalculates players and weapons up to 60 frames after a stat change, and in the solo view those of players at index 1+ would read `RunData` slots that no longer exist. The solo `UpgradesUI` set itself up as nothing in `_ready` (the run was coop then), so its `_ready` runs again once in the solo view. Then the challenge UI, then the solo `shop.tscn`, still in the solo view.
   **Choice time:** entering the solo view sets `LanNet.choice_deadline_msec` (now + `lobby_settings.choice_time`, default `NetProtocol.DEFAULT_CHOICE_TIME` = 90 s, 0 = no limit; the host picks it on the lobby's settings page, `NetProtocol.CHOICE_TIMES`). Each machine counts its own time from its own solo view. A `LanChoiceCountdown` shows the seconds left in place of the wave timer (main's `_wave_timer_label`, its `wave_timer` cleared; "NEXT WAVE IN" replaces the wave number above it), on the shop's Go ("Ready (42)") and on the waiting overlay's back button ("Back to the shop (42)"), red for the last 10 s. At 0 main picks a random upgrade (`_old_upgrades`, the options shown) and takes crate items through the container's handlers, one per frame outside its button delay; the shop closes the pause menu and presses Go, and Go can't be taken back any more (`_clear_go_button_pressed` returns, back button disabled). The host goes on `CHOICE_GRACE` (10 s) after its own deadline without the missing results (`_process` → `_on_all_shops_done`); those players keep their wave-end state and lose their pending level-ups. A client still in the upgrade screen then enters the wave from `main.tscn` (`_rpc_enter_wave` accepts a wave scene whose end-wave timer ran).
7. **Shop**: the `base_shop.gd` extension's Go marks the candy-bag item locking, shows `ui/shop_waiting_overlay.gd` and calls `LanNet.send_shop_done(true)`: the own solo run (JSON) goes to the host as `_rpc_shop_done(wave, json)`; "Back to the shop" or cancel sends `""`. The host keeps the runs (`_shop_runs`), waits for itself and every connected client that didn't quit (`_left_run_peers`, from `_rpc_left_wave`, which a client also sends when it reaches the title screen between waves without having pressed Go), and broadcasts who is still shopping (`_rpc_shop_waiting(names)`).
8. **Next wave**: once nobody is shopping, the host leaves its solo view (its own result is what that leaves in its slot), merges every other result into its player's slot (`RunBuilder.merge_solo_run`: `players_data`, `locked_shop_items`, `tracked_item_effects`; players without a result keep their wave-end state), runs `RunBuilder.apply_go()` (vanilla's once-for-all Go parts: hourglass, extra-elite roll (neutral elites), `current_wave = RunData.get_next_wave()`, the lifeform scanner turning the next elite wave into a horde, then cursing locked items as the shop's `_on_tree_exited` would) and sends the run like Start (`_send_run`: new run id, `_rpc_run_state`, acks, `_rpc_enter_wave`). A client leaves its solo view before applying it. Clients that quit to the lobby get it too and are back in (the host ignores lobby entry changes while a run is in progress). A digest mismatch here logs a warning and the wave starts anyway with the host's run (at Start it keeps everyone in the lobby). At the next wave the host kills the players of disconnected entries again (`LanWaveSync._kill_disconnected_players`).
9. **Run end** (everyone dead, which always ends the run in a session (no retry screen), or the last wave won): the host still sends the wave-end state; every peer stops `LanWaveSync`, sets `LanNet.run_over`, enters the solo view without the shop phase (`enter_solo_view(false)`), puts back `RunData.run_won` and `difficulty_unlocked` (set by `apply_run_won` in `clean_up_room`, cleared by applying the host's run) and opens the solo `end_run.tscn`. The `base_end_run.gd` extension hides Restart and New Run and turns Exit into "Back to the lobby"; the `end_run.gd` extension adds a player list left of the stats (`ui/end_run_player_list.gd`, own player first shown, by index or the mode's ranking; the inventories get fewer columns to make room) whose rows show another player's stats, weapons and items via `solo_view.show_player`. Rewards stay the own ones. A client back in the lobby while the host is still on its end screen sees "The run is over…": `LanNet.set_run_over()` sets `run_over` on every machine, and the host also sets `lobby_settings.run_over` and broadcasts it, which reaches clients that quit to the lobby or rejoined before the run ended (cleared with `set_run_in_progress`).
10. **Back to the lobby** (from the end screen, or the host quits): the title screen's vanilla `_ready` resets `RunData`; its extension calls `LanNet.on_title_screen()` (a client that hadn't pressed Go sends `_rpc_left_wave`; any solo view is discarded), reopens the lobby and (host) calls `set_run_in_progress(false)`, which drops disconnected players, un-readies everyone (so each player can pick another character before the next run) and makes the run stale. Clients in `main.tscn` or the shop follow when a lobby broadcast says `in_wave` is false. A disconnect during a run keeps the run id (`_broadcast_lobby_state(run_in_progress)`), so a next-wave sync in progress isn't dropped.
11. **Leave / errors**: `_end_session(reason)` restores unlocks and saves, resets RunData if a synced run replaced it, and returns to the title screen with a reason popup. The host sends `_rpc_bye` to every client first (also from `LanNet._exit_tree`, when the game is closed mid-run), so a client can tell a closed session from a lost connection.
12. **Rejoin after a lost connection** (clients, during a run): the host gives every client a random token with `_rpc_welcome(player_index, rejoin_token)` (host: `_rejoin_tokens`, peer id → token); the client saves it in its config and sends it in every hello (`rejoin_token`, 0 = none). A client whose connection breaks during a run (`server_disconnected` while `lobby_settings.in_wave`, no `_rpc_bye` before) ends the session with `LAN_MSG_RECONNECTING` (title screen, Join page as "connecting", Back cancels) and calls `join(config.last_ip, config.port)` again `RECONNECT_INTERVAL` (2 s) after each failed attempt, for `RECONNECT_TIME` (60 s), then `LAN_MSG_RECONNECT_FAILED`. During a run the host answers a hello with a known token with `_rejoin`: the slot gets the new peer id and `connected = true`; the peer goes into `_left_run_peers` (not waited for in this wave or shop phase); an old connection the host hasn't seen time out yet is dropped and its player killed; the client gets the welcome and the lobby state, and the next wave's run if one is waiting for acks. From there it is a player who quit to the lobby: back in at the next wave with the gear from the last wave end (a shop phase it missed keeps its wave-end state, its pending level-ups are lost). A restarted game rejoins the same way from the Join page (the token is in the config, the beacon runs during a run). Not covered: rejoining into the running wave or the shop phase; a lost host ends the run.

## Connection, menus and lobby (Steps 1–3, 8b)
**Connection** (`LanNet`): ENet, port 24567 by default (`net_config`), at most 11 clients. ENet's default timeouts keep a connection through a few seconds of silence (a short cable pull just stalls the game); a client noticed the loss of a killed host after about 10 s, and a failed connect attempt takes about 30 s. `server_relay` is off, every RPC checks the sender id and argument types, peers without a hello within 5 s are kicked, rejected clients get the reason and are kicked 0.5 s later. Reasons are translation keys (`LAN_REJECT_*`, `LAN_MSG_*`); `last_end_reason` keeps the last one for the page that opens next. Player indices are compacted when someone leaves the lobby; during a run the slot stays with `connected = false` and `player_disconnected` fires.

**Unlocks:** during a session every peer has everything unlocked (`NetProtocol.get_multiplayer_unlocks()`, from the loaded game data), so item pools match on every machine (the handshake already checks game version and DLCs). Covers `zones/characters/upgrades/consumables/weapons/items_unlocked`, not difficulties (all are selectable in the lobby anyway); consumables follow vanilla's unlock-all save. Vanilla's `unlock_all_*` aren't used (they also change bought-item counts, kills and challenges). Restored on leave; disk saves are blocked meanwhile, except `LanNet._save_own_progress`.

**Item sets** (new in 1.2.0.1: the base game, each DLC and the free updates New Dawn and Paws 'n Claws are sets the main menu can switch off): the host's apply to the whole session. `host()` stores its `ProgressData.active_update_data` in `lobby_settings.item_sets`; a client takes them from `_rpc_welcome` (before its lobby opens) and again with every lobby state (`_apply_host_item_sets`: `ProgressData.apply_run_update_data` with `NetProtocol.get_valid_item_sets`, the ids it knows and owns, then `ItemService.init_unlocked_pool`), as vanilla's Continue applies a run's sets. The run carries them too (`RunData.active_update_data_ids`). `_end_session` puts back the own (`refresh_active_update_data`; the own selection, `deactivated_update_data`, is never touched). `LobbyRules` leaves out what vanilla's selection pages grey out: a character whose `required_item_set` is off (`ItemService.get_disabled_required_update`), a starting weapon or item from a set that is off (`is_choice_available`), and a character with starting choices but none left; the grids don't show them and the host refuses them. Should the sets change while the lobby is open, it refills the character grid.

**Several starting weapons** (Survivor: `extra_starting_weapon_choices`): a lobby entry's `weapon_ids` holds the picks in order, `LobbyRules.get_pick_count` of them (1 + the character's effect values); the same one twice is allowed, as in vanilla. Each press in the weapon grid adds a pick, a press with all picks made starts over; the label reads "Weapons (1/2)" (short enough for the column: a longer one widened it and shifted the layout) and each picked element shows its count. Ready needs all picks (`is_entry_complete`). `build_run` adds each with `add_weapon(…, true)`, which fills `selected_weapon` and then `extra_selected_weapons`. The player row shows every pick's icon.

**Progress** (what a session counts for on the own save, `game/session_progress.gd`, decided 2026-10-21): a won run credits only the own character (the `run_data.gd` extension runs vanilla's `apply_run_won` in the solo view, with `is_coop_run` still true): its challenge, difficulty record and the next danger. Between waves (solo view) everything is the own player's. During a wave challenges and lifetime counters count for the team: the `challenge_service.gd` extension lets only the host complete them and forwards each (`LanNet.forward_challenge` → `_rpc_challenge`, once per wave); `try_complete_challenge` skips vanilla's early return for challenges the host already has, so clients still get them. Clients ignore their own in-wave completions. Counters (`ProgressData.data` numbers, `killed_enemies`, `killed_by_enemies`) are noted at each wave's start (`LanNet.on_wave_started`, from `LanWaveSync._ready`); the host sends their change with the wave-end state and clients set start + change. Lifetime-count challenges (`check_counted_challenges`) stay each machine's own, checked by clients after taking over the counts. Rewards of challenges completed in the session go into the own unlock lists (`progress.apply_rewards`), which the session swaps for "everything". `LanNet._save_own_progress` (own lists plus rewards, own "Continue" run, `ProgressData.save()`, then everything unlocked again) runs on the title screen during a session (after each run) and when the session ends.

**Pages** (built in code with `ui/ui_kit.gd`, added by the `title_screen_menus.gd` extension): Main menu → Multiplayer (name, Host game, Join game) → host: Lobby; join: Join page (discovered games as rows "name n/12", incompatible ones disabled; "IP or IP:port" field, `NetProtocol.parse_address`) → Lobby. Leaving the lobby returns to the page it was entered from; session-end reasons show in that page's status line. On title load the extension reopens the Join page (if `last_end_reason` is set) or the lobby (if still joined).

**Discovery** (`net/net_discovery.gd`, `/root/LanNet/Discovery`): while hosting (also during a run, for rejoins after a restart), a JSON beacon every second to UDP 24568, sent to `255.255.255.255` plus the /24 broadcast of each private LAN address (Linux sends the limited broadcast only on the default interface). The Join page listens only while visible; games expire 10 s after their last beacon (`GAME_TIMEOUT`; a power-saving WiFi client misses broadcasts for up to ~5 s, so a shorter timeout made the list flicker). `NetProtocol.get_lan_addresses` skips loopback, link-local and docker/bridge/VM interfaces; `get_primary_lan_address` (shown to the host as `IP: ip:port`) prefers private addresses, wired before wireless, and skips Windows virtual adapters.

**Lobby** (`ui/lobby.gd`; rules in `net/lobby_rules.gd`, shared by the UI, the host's validation in `_apply_player_changes` and `are_all_ready()`):
- **Layout:** the page's column is the screen's height minus 40 px above and below (`_fit_to_screen`, again on `size_changed`), the same for host and client, so Leave, Start and Ready sit at the bottom. Left (620 px): address (host), player count, player list (colour, character icon, name and tags, weapon icons, Ready/Choosing; takes the height left over, min 200 px, scrolls), the host's Settings button, the settings summary, the status line (only when there is one), Leave and Start. Right: character grid (9 columns, 760 px) and starting-weapon grid (4 columns), each with its preview below; Ready under the weapon preview (preview + Ready = 440 px, the character preview's height). The grids scroll and take the height the previews leave (min 150 px), so previews and Ready end level with Leave and Start. The weapon area keeps its height when the no-choice text replaces the grid.
- **Grids** are vanilla `inventory.tscn` with random tiles (resolved locally, the real id is sent) and lock tiles. Picks get, as in vanilla's coop selection, a half transparent background in the player's colour (`LanSelectedFill`, the element's first child, behind the icon) and a border in it (`LanSelectedMarker`, last child, over the element's frame). Starting weapons use the same filter as `weapon_selection.gd`.
- **Previews:** vanilla's small `item_panel_ui.tscn` for both (icon box hidden, the name's scroll box 64 px, description scrolls with `expand_indefinitely = false` set before `_ready`, its scroll box fills the panel). The character preview adds the starting weapons and items as a vanilla `Inventory` with vanilla's `ItemPopup` (the page's last child; `display_item_data`, which doesn't read run data); refilled only when the shown character changes. What a preview shows: with the cursor visible the last hovered element (a hover ends when the mouse leaves the grid *and* its preview); with it hidden the focused one (kept while focus moves into its starting items, checked deferred); else the player's pick.
- **Focus:** character → weapons → Ready once the host confirmed each pick; "left" from the weapon grid's first column goes to the picked character ("up" from Ready when there is no weapon choice). Left and right on the bottom row move only between Leave, Start and Ready (a hidden Start or a disabled Ready is skipped); up and down leave it.
- **Settings:** under the player list a full-width Settings button for everyone, then a summary line for everyone (`SettingsPage.get_summary`: the mode's name unless co-op, "Zone · Danger N", then settings that differ from their default, e.g. "60 s to choose"; wraps to two lines). A mode with teams adds a full-width "Switch team" button above Settings for everyone (the player's `team` entry, `_rpc_update_player`; not during a run), lists the players by team under a header in the team's colour with its player count ("Team Red (2)"); a click on a header joins that team (a flat, unfocusable button: mouse only, gamepads use Switch team). It opens `ui/settings_page.gd` over the lobby (last child, opaque background that takes clicks): rows in three groups under small headers: Game (Mode, item ids are indices into `ModeRegistry.MODES`; Zone; Danger), Balance (Enemy scaling, Time to choose), Loot (Materials: Split among all / Picker keeps, Crates: Any player / Picker keeps; ids 1 / 0, `lobby_settings.share_materials` / `share_crates`, remembered as `last_share_*`). A fixed-height help box under the rows explains the row under the mouse (on mouse motion, `_input`) or else the focused one: the scaling's percentages per extra player, the choice time, the loot options; any other row, and nothing focused, shows the mode's description. Loot rows the mode fixes (its `FIXED_SETTINGS` constant, `ModeRegistry.get_fixed_settings`) stay, dimmed, disabled and showing only "Set by mode" (item id 2; `add_item` takes -1 as "use the index"), their help is the mode's description, and the summary leaves them out. One `OptionButton` per row whose item ids are the values (every `ZoneService.zones` and `ItemService.difficulties` entry, Danger 0–5 always; `CHOICE_TIMES`; preset index). A change goes to `set_lobby_settings` at once (host only and not during a run. Read-only (clients, the host during a run) the dropdowns still open and focus, but every list entry is `set_item_disabled`, and a note under the title says why: "Only the host can change the settings." / "... during a run"; validated in `_apply_lobby_settings`, remembered as `last_zone` / `last_difficulty` / `last_choice_time` / `last_scaling_preset`). The scaling preset (`lobby_settings.scaling_preset`, `NetProtocol.SCALING_PRESET_FACTORS` 0.6 / 1 / 1.5) rewrites `lobby_settings.scaling`: the config's `SCALED_BY_PRESET` knobs (enemy count, HP, HP beyond 4, damage) times the factor; arena and cap stay. Clients only read the knobs (`LanGame.get_scaling`). Focus is chained top to bottom within the page (the lobby's controls stay visible to Godot's focus search). Back or `ui_cancel` (the lobby's `_input`; not while a dropdown is open) closes it and focuses the Settings button. A new setting: a `lobby_settings` default, validation and config entry, a row, a summary part. Start is enabled when `are_all_ready()`. Changing character or weapon un-readies; the host drops invalid or locked picks and ignores entry changes during a run.
- **Status line:** only while something is going on: run sync (pending, synced, failed), a wave in progress, run over (`run_over`); hidden otherwise. It wraps (at most two lines), so a long hint can't widen the left column (waiting for picks or Start shows in the player list and the Start button).

## Scaling and 12 players (Steps 4–5)
- **Arrays:** vanilla's 4-slot per-player arrays grow to 12 **always** (`LanGame.grow`), not only in a session; vanilla never reads slots beyond the player count. They grow in the extensions' `_init` and after the vanilla functions that reassign 4-slot literals (`RunData.reset`, `_reset_per_wave_properties`, `reset_run_caches`, `resume_from_state`; `Utils.reset_stat_caches`, `reset_last_elt_selected`; `Utils._manual_aim_cache` on demand in `is_manual_aim`, since `_process` resets it). `TempStats` / `LinkedStats` are grown once from `LanNet._ready`. `DebugService.log_run_info` gets grown arguments. The coop `UpgradesUI` is turned off (`is_coop_ui = false` in main's `_enter_tree`).
- **HUD:** main's `_enter_tree` copies the P4 node sets (`LifeContainerP4`, `PlayerLifeBarContainerP4`, `UIThingsToProcessPlayerContainer4`) as P5–P12 before vanilla's `_ready` looks them up by `%` name. The local player's HUD takes P1's slot; other screen HUDs are hidden. Others get a `LanNameLabel` (copy of `font_smallest_text`, size 22, 2 px outline, `Rect2(-150, -106, 300, 32)`) and an always-visible bar over their head; dead ones a greyed name and the goat skull (`LanDeadIcon`).
- **Off-screen arrows** (`game/offscreen_arrows.gd`): a `Control` in main's `UI` layer above the damage vignette (below HUD and pause menu); a triangle in the player's colour, 36 px inside the screen edge, for every living non-local player outside the viewport. Hidden from cleanup on.
- **Colours:** 4 vanilla + 8 extra `[hue, value]` pairs (`Color.from_hsv(h, 0.3, v)`; `get_player_color` adds 0.5 saturation): blue, pink, purple, red, spring green, magenta, azure, brown.
- **Spawn:** players on a circle of radius `60 + 15n` around the map centre.
- **Knobs** (`NetProtocol.DEFAULT_SCALING`, per extra player; the host reads them from `[scaling]` in `user://lan_coop.cfg`, clamped to 0–2, and sends them in `lobby_settings.scaling`; `LanGame.get_scaling(key)`):

  | Knob | Default | Effect |
  |---|---|---|
  | `arena_area_per_player` | 0.25 | width/height × `sqrt(1 + 0.25(n-1))` (1.94× at 12), applied after vanilla's `map_size` effect |
  | `enemy_count_per_player` | 0.3 | spawn count `1 + 0.3(n-1)`, but only up to the player count where the cap stops growing (`LanGame.get_count_players`, 7: 2.8×); `CoopService.additional_enemies_per_coop_player` gets the average over all extra players |
  | `enemy_health_per_player` | 0.3 | HP for players 2–4 … |
  | `enemy_health_per_player_beyond_4` | 0.2 | … and beyond (averaged: 3.5× at 12 instead of 4.3×), times the spawn count cut off above 7 players (12: 4.3 / 2.8 → 5.4×) |
  | `enemy_damage_per_player` | 0.08 | damage |
  | `enemy_cap_per_player` | 0.25 | `max_enemies × min(1 + 0.25(n-1), 2.5)` (250 from 7 players, `LanGame.MAX_ENEMY_CAP_FACTOR`) instead of vanilla's `(n-1)/8`; past ~300 enemies vanilla physics can't keep 60 ticks a second. Vanilla enforces the cap only at a group spawn, so queued enemies can push past it for a while (~285 seen) |

  Above 7 players the count stops because the cap does: vanilla would cull random enemies without loot at every group spawn. Count × HP stays the same (12: 2.8 × 5.4 ≈ 4.3 × 3.5), and vanilla's coop material bonus (`get_additional_materials_per_coop_player`, from players ÷ count) rises with the lower count (12: 3.6× per enemy instead of 2.4×), so materials per player keep up.
  `LanGame.apply_enemy_scaling(n)` runs in main's `_enter_tree`; `CoopService.clear()` on the main menu restores vanilla's values. Danger effects are read from player 0 only, `double_boss` is summed.
- **Physics quirk fixes (session only, no gameplay change):** each unit's burning `SpreadArea` (r = 128, enemies mask) starts disabled; vanilla leaves it on from the start and only `apply_burning` needs it (`extensions/particles/burning/burning_particles.gd`). Enemy hitboxes move from the enemies layer to `LanGame.ENEMY_HITBOX_BIT` (layer 20, `enemy.gd` `_ready`), and hurtboxes with the enemies bit in their mask (players, scapegoat) get it too (`overlap/hurtbox.gd`). Both cut collision pairs about fivefold at 400 enemies (measurements in [lan-coop-plan.md](lan-coop-plan.md#performance)).
- **Spawn rate** is vanilla's: queued enemies are released 1 (2 with 110+ queued) every 3 physics frames, whatever the player count.
- **Camera:** each machine follows only its own player (solo behaviour, `lock_coop_camera` ignored); after its death, vanilla's coop camera over the living players.

## Between waves (Step 7)
**Idea:** the vanilla coop upgrade UI, shop and end screen have 4 player slots and assume one screen. Instead every machine shows the vanilla **solo** screens for its own player: `RunData` temporarily becomes that player's solo run (the solo view), and the host merges the results.

**State in `LanNet`:**
| Name | Meaning |
|---|---|
| `wave_end_state` | `{wave, pending, ok}`: the run after the wave was applied (host: sent). Cleared when a wave is entered (`_reset_between_waves`), since a new run starts at wave 1 again. |
| `solo_view` (`game/solo_view.gd`) | `enter(index, local device)` / `leave()` / `discard()` / `show_player(index)` (end screen: another player's data and `MOVED_ARRAYS` slots in slot 0, `shown_index`; `leave()` puts the own one back first). Moves `players_data[index]` and the per-player `RunData` arrays (`MOVED_ARRAYS`) to slot 0 and back; resets per-player caches. Use `LanNet.enter_solo_view(shopping)` / `leave_solo_view()`. |
| `between_waves`, `shop_done`, `shop_waiting_names` | upgrades and shop phase; set by `enter_solo_view(true)` |
| `choice_deadline_msec` | between waves: when the own choice time ends (`OS.get_ticks_msec`), 0 = no limit; `get_choice_time_left()` |
| `_shop_runs` (host) | player_index → that player's solo run JSON from Go |
| `_left_run_peers` (host) | clients that quit the run (not waited for); cleared when a wave is entered |
| `run_over` | the run ended and the end screen was shown (lobby hint) |
| `_run_id_counter` vs `lobby_settings.run_id` | the run the clients hold vs the lobby's current run (a lobby broadcast can reset the latter; wave-end states use the counter) |

**RPCs** (besides `_rpc_run_state` / `_rpc_run_state_ack` / `_rpc_enter_wave`, which Start and every next wave share via `_send_run`):
| RPC | Direction | Content |
|---|---|---|
| `_rpc_challenge(chal_id)` | host → clients | a challenge completed in the wave (team credit), once per wave each |
| `_rpc_wave_end_state(run_id, wave, json, digest, pending, counters)` | host → clients | the run after the wave, `[[levels], [consumable ids]]` per player and the wave's counter changes `{data, killed_enemies, killed_by_enemies}`; applied once the client's own wave is over |
| `_rpc_wave_end_ack(wave, ok)` | client → host | digest check result |
| `_rpc_shop_done(wave, json)` | client → host | Go: the own solo run; `""` = back to the shop |
| `_rpc_shop_waiting(names)` | host → clients | who is still shopping |
| `_rpc_mode_state(serial, mode_id, state)` | host → clients | the run's game mode and its state ([Game modes](#game-modes)) |
| `_rpc_mode_message(payload)` | both | a mode's request or answer (array) |
| `_rpc_left_wave()` | client → host | quit the run (pause menu in the wave, or reaching the title screen between waves without Go) |
| `_rpc_bye()` | host → clients | the session closes (no rejoin attempt) |

**Order on every machine:** `main._on_EndWaveTimer_timeout` → host `send_wave_end_state` / client waits for `lan_wave_end_ready` (main's relay of `LanNet.wave_end_ready`) → `LanWaveSync.stop()` → run end: `enter_solo_view(false)`, `end_run.tscn`; otherwise `enter_solo_view()`, solo `UpgradesUI` (its `_ready` run again), `shop.tscn` → Go → host merges when nobody is shopping → next run via `_send_run` → client leaves the solo view in `_rpc_run_state` → `_rpc_enter_wave`.

## In-wave sync (`LanWaveSync`)
**Authority:** each machine moves its own player; the host simulates everything else. Clients spawn copies of host entities through vanilla code, then make them inert (`_make_inert`: no physics process, kinematic, areas neither monitoring nor monitorable, collision mask reduced to the walls bit so copies don't pair with each other; the layer stays so client weapon ranges still see them).

**RPCs** (all on `LanNet`, which forwards to `LanNet.wave_sync`; every remote func checks sender and argument types):
| RPC | Direction | Mode | Content |
|---|---|---|---|
| `_rpc_player_state(time, pos, move, aim, manual_aim)` | client → host | unreliable, every physics frame | own player; `time` is the client's msec when sent; `aim` is the aim point relative to the player (mouse, or gamepad aim × 10000) |
| `_rpc_snapshot(bytes)` | host → clients | unreliable, every 3 physics frames (20 Hz) | layout below |
| `_rpc_events(array)` | host → clients | reliable, once per physics frame if any | event list below |
| `_rpc_wave_loaded()` | client → host | reliable | wave scene is up |
| `_rpc_left_wave()` | client → host | reliable | quit the wave (pause menu) |
| `_rpc_wave_cleanup([failed, lost, won])` | host → clients | reliable | wave over, host's verdict |

**Snapshot** (`StreamPeerBuffer`): header 18 bytes (seq u32, host msec u32, `time_left` f32, flags u8 (1 = waiting for clients), `EntityService.enemy_time_factor` f32, player count u8); per player 37 bytes (pos f32×2, move s8×2 (×127), speed f32, hp s32, max hp s32, flags u8 (1 = dead, 2 = acid tint, 4 = petrol tint: Primal Dread's puddles, which only have areas on the host), gold s32, xp f64 (exact: XP gain bonuses make it fractional), level u16); then entity count u16 and 8 bytes per entity (net id u16, x/y s16, HP ratio u8 (0–255), flags u8 (1 = burning, enemy outlines: 2 = boosted, 4 = cursed, 8 = charmed; 16 = full lung (the DLC's iron and spiky lungs, their sprite), 32 = mirrored lung (random per machine in its `_ready`), 64 = angry stargazer (clients switch its movement behaviour and play its angry sound when it turns on), 128 = hidden (Primal Dread's oviraptor and iguanodon, `GoTowardsBorderOppositeMovementBehavior`, wait unseen at the map's edge and show when they charge; clients hide the copy at its spawn with the rustling sound and fern shake, show it with the charge sound, and turn it along its path in `_update_puppets`))). Trees are left out (static). Clients drop older seqs and render puppets at a render clock behind the host (`_update_puppets`): the delay is 100 ms, or the largest snapshot lateness of the last 5 s plus 10 ms (up to 300 ms; WiFi power saving delivers snapshots in bursts up to ~170 ms late), taken at once when it grows and slowly when it shrinks. The clock offset follows the fastest snapshot and creeps up 1 ms/s for clock drift. The render clock advances by the physics step and runs at most ±10 % fast or slow towards its target, so puppets move the same amount every tick and offset or delay changes never jump.

`LanWaveSync.event_counts` counts sent (host) / received (client) events per code.

**Shared random rolls:** what `main._ready` places at random and players walk into is rolled from `lobby_settings.wave_seed` on every machine: the hole layout, dig sites, poacher zones and the zone decoration (`LanGame.begin_shared_random(tag)` seeds the global RNG with the seed, wave and tag; `end_shared_random` randomizes it again). The holes come first, so the free cells `ZoneService.get_rand_pos` picks from are the same everywhere.

**Brachiosaurus (Primal Dread boss):** its state timer (20 s per state) runs only on the host (extension); clients take its state from event 27, its position from the snapshot (no edge tweens on clients: `stay_edges_of_map_movement_behavior.gd`), shown/hidden and facing from the snapshot flags.

**Holes and time slow (Primal Dread):** a jungle wave with `spawn_holes` instances one of several prepared hole layouts at random in `main._ready`. Holes are obstacles, so every machine needs the same one: in a session the `gpe_spawner.gd` extension picks it from `hash([lobby_settings.wave_seed, current_wave])`; the host draws a new `wave_seed` for each run it sends (`_send_run`), and the lobby state carries it before the wave loads. The enemy time slow (time shifter, pocket watch; `EntityService.slow_enemy_time`) runs on the host; clients take the snapshot's factor into `EntityService` (with a remaining time that only the host's 1.0 ends), so enemy projectiles fly slower (`Projectile._get_time_factor`), `_update_puppets` slows the enemy copies' animations (`Enemy._apply_time_factor_to_animation`, which the copies' disabled physics would run), and `ShiftTimeVisualEffect` shows through `enemy_time_slow_changed`.

**Ids:** entities, projectiles, items, puddles and spawn markers each have their own u16 counter (wrapping). Pooled nodes keep their id in a member (`lan_net_id` on projectiles and items) or meta (`lan_net_id` on entities, `lan_birth_id` on markers) and stale ids pointing at a reused node are ignored.

**Client side:** wave manager and entity spawner physics off, structure timer stopped, local loot and drops blocked (`spawn_loot`, `spawn_gold`, `spawn_consumables`, garden fruit), weapons never fire (`should_shoot`), players never fire alien eyes (`on_alien_eyes_timeout`; the host's volleys come as projectile events, the local ones were a second volley), enemy/turret `shoot()`/`start_shoot()` and `ShootingAttackBehavior.shoot()` no-ops (animations, including a charmed enemy's `shoot_charmed`, still play; the DLC's pufferfish shoot from `die()`, which clients call on their copies), own player has no hurtbox, no pickup/attract areas, no regen, speed and HP from the host, no scene effect behaviours (the DLC's enemy curse rolls on the host; the snapshot carries the outlines). "Inert" copies: `set_physics_process(false)`, `MODE_KINEMATIC`, every `Area2D` in the subtree `monitoring`/`monitorable` false (deferred). Client entity HP is the 0–255 ratio (`max_stats.health = 255`).

**Host side:** remote players are `lan_net_driven` (`get_movement()` = reported move, zero velocity). Their position is dead-reckoned (`_apply_remote_states`): the reported position moved on at the velocity between the client's last two states (capped at the host's speed; 0 after a gap over 0.25 s) for the state's age, at most 0.25 s. Not the pressed direction: a client blocked by the host player would be moved into it, and the host's kinematic player would push itself out. The copy is moved there like vanilla moves units (`_move_remote_player`: `test_motion`, then a slide; more than 200 px is jumped), so it stops at the host's player instead of overlapping it. Then `_on_moved` with the distance, as `Unit._physics_process` does after its own move: effect behaviours count it (the DLC's steps: the hiker's gold and max HP, lifetime steps; before, the host counted no steps for remote players). The age comes from `time` and a per-client clock offset tracked like the snapshot clock (fastest state, +1 ms/s). A new state's difference to where the old one would show the player this tick fades out (×0.75 per tick; above 200 px it snaps). Over WiFi with power saving a client's states arrive in bursts with gaps up to ~200 ms; without this the player froze and jumped on the host, and enemies aimed at and hit a stale copy. Remote players' manual aim comes from `get_remote_manual_aim`, and their weapons turn towards `get_remote_aim_point` (the `weapon.gd` extension's `get_global_mouse_position`; remote players count as keyboard players on the host). The wave timer waits for `_rpc_wave_loaded` from every client (15 s at most). Disconnect or `_rpc_left_wave` kills that player; disconnected players are killed again at the start of each later wave.

## Game modes
Ideas, effort and the order they came in: [lan-coop-modes.md](lan-coop-modes.md). Picked on the lobby's settings page (`lobby_settings.mode`, remembered as `last_mode`); the driver's `MODE=id` sets it for a test.

**Layer:** `LanNet.mode` is never null: a `LanMode` (`modes/lan_mode.gd`) or a subclass. Shared code asks it at fixed hook points and never checks which mode is active; the base class answers with plain co-op. The host builds it at Start; a client builds its own from the host's first `_rpc_mode_state` of the run (a new serial or id builds a new instance). Hooks:
| Area | Hooks (host only unless "both") |
|---|---|
| Lifecycle | `start(players)` (Start; may change the run), `set_state` (client), `on_wave_started(main)` (both, `LanWaveSync._ready`; the base adds the scoreboard when the mode has score columns), `on_wave_physics` (both), `on_player_died` (both, before vanilla's `_on_player_died`), `on_entity_died` (synced entities, not at cleanup; the base counts `kills` from `killed_by_player_index`, never from `Utils.default_die_args`), `on_enemy_killed`, `adjust_run_states([failed, lost, won])`, `on_wave_end()` (before the wave-end run is sent), `is_player_out` (both) |
| Combat | `uses_pvp()`, `can_target(weapon, body)`, `can_hit(target, hitbox)`, `scale_player_damage`, `get_enemy_targets(enemy, players)` (null = all) |
| Loot | `get_material_receivers(picker)` (null = everyone, as vanilla; the base follows `lobby_settings.share_materials`: off = `[picker]`), `shares_crates()` (the base: `share_crates`, the host's for everyone instead of each machine's `share_coop_loot`), `on_materials_collected`. A mode that decides these itself lists the settings in `FIXED_SETTINGS` (Gold Rush, Team Race, `elimination_mode.gd`; `get_fixed_settings` also reads a base script's) |
| Arena and spawns (both) | `get_scaling_player_count`, `get_enemy_cap_factor`, `get_arena_size`, `get_player_spawn_position`, `on_entity_spawned(entity, data)` (host), `on_group_queued(spawner, sizes_before)` (host) |
| Shop (both, solo view) | `on_shop_ready`, `get_shop_items`, `intercept_shop_buy`, `blocks_reroll`, `allows_item_locking`, `on_shop_state_changed` |
| Scores and results (both) | `get_score_columns` (`[key, label key, icon]`; the icon heads the scoreboard column), `get_rank_key` / `get_ranking`, `get_group` / `get_group_title` / `get_group_color` / `get_group_status` (teams: a header on the scoreboard and a frame on the end screen's list, status icons only on the scoreboard, ranks within the group; the ranking keeps a group together), `get_player_status` (`{icon, text, muted}` next to the name instead of words (the end screen's list shows only the text): "(W7)" without icon via `get_out_status`, boss icon, crown for the winner; `muted` greys the row, `out` fades a team's frame), `get_banner(main)`, `get_leader`, `get_end_title`, `get_result_text`, `has_results` (the end screen's list shows winner and scores), `on_end_screen` (title) |

**State and messages:** `mode.state` holds plain values only; the host calls `mark_dirty()` and `LanNet._process` sends it (`_rpc_mode_state(serial, mode_id, state)`, at most every `NetProtocol.MODE_STATE_INTERVAL` = 0.1 s; at Start, before every wave-end state and to a rejoining client at once). Requests and answers go as `_rpc_mode_message(payload)` both ways (`mode.send_message` client → host, `send_message_to(player_index)` host → one player; the host's own go straight to its mode). Visuals that only depend on the wave timer, the wave number and a seed in the state (storm, hill) are computed on every machine without traffic. A mode ends a wave early with `main.lan_end_wave_now()` (host: as if the timer ran out). Competitive modes end the run as "run lost" for everyone (no character win credit); the title and the results say who won. Mode texts live in each mode's `STRINGS` (`{locale: {key: text}}`, en and de), shared ones in the registry's.

**Modes as built** (the constants at the top of each file are the tuning knobs; balance is untested in play):
| Mode (id) | Rules |

## Pitfalls learned
- **Errors disable the mod**: any `ERROR:` / `SCRIPT ERROR:` mentioning `mods-unpacked` triggers the crash reporter on the next Steam/Epic launch. Vanilla `push_error` and failed `assert`s in vanilla code called from an extension are attributed to the extension's file. Check logs after every test.
- **Parse errors** make an extension silently absent; run the driver's `quit` role after edits. `var x: = <untyped expr>` and duplicate `var` names in one scope are the usual causes.
- **Early extensions (shipped game):** after each extension ModLoader `reload()`s the base's vanilla `class_name` children. In the shipped game those are `.gdc` without source, and the reload empties them (the game didn't start at all with the 1.12.0 zip; [modding.md](brotato/modding.md#script-extensions-rules-and-gotchas)). So `mod_main.gd` installs `EARLY_EXTENSIONS` itself with `take_over_path` in its `_init`, before ModLoader compiles any extension: the bases with subclasses (`item`, `projectile`, `weapon`, `enemy`, `turret`, `player`; `base_shop` in `_ready`, see below) and the classes in vanilla signatures that a script or its subclass overrides (`entity_birth`: `on_entity_birth_timeout(EntityBirth)`; `shop_item`: `_on_shop_item_focused(ShopItem, int)`). Every subclass, grandchildren included (Monk, Rhino, BulletHellProjectile, …), then finds the extension at its base's path when it loads, with no reload. `_early_extensions` holds them (the resource cache doesn't). An extension added for a class with subclasses, or for a class in an overridden signature, belongs in that list; ModLoader would break it in the shipped build only, which the test copy never shows. Check with the shipped build ([testing.md](testing.md#shipped-game-and-windows)).
- **Early extensions and autoload types:** mods run `_init` inside ModLoader's (an early autoload), when the later autoloads' names have no type yet. A vanilla script that infers a type from one (`var next_wave: = RunData.get_next_wave()`, `base_shop.gd` since 1.2.0.1) fails to parse if loaded then ("The assigned value doesn't have a set type"), and its extension with it. Such bases go into `READY_EXTENSIONS`, installed the same way at the start of `mod_main._ready` (every autoload is instanced by then, and nothing has loaded the shop yet). Check new vanilla versions for `: = <Autoload>.` in the early bases.
- **Engine callbacks run at every inheritance level.** `_ready` goes base → derived; `_input`, `_process`, `_physics_process` go derived → base. An extension can't suppress vanilla's callback; switch processing off or override the regular methods it calls.
- **Pools:** `main.add_node_to_pool` asserts that the pool exists; create it with `get_node_from_pool` first. Pooled nodes are removed from the tree and re-added, `_ready` runs only once.
- **Coop UI vs one player per machine:** an active FocusEmulator swallows all mouse input; `InputService` hides the cursor on every input in a coop run with more than one player; coop UI asks `FocusEmulatorSignal` for the focusing player and `push_error`s on -1. Sessions use native focus and the solo mouse rule instead.
- **`Utils.is_manual_aim` returns null** when no manual-aim setting is on; compare with `== true`.
- **GDScript 1 constructors:** a subclass without its own `_init` can't be built with arguments (`Sub.new(a, b)`: "Expected 0 arguments"), even if the parent's `_init` takes them. Modes are built with `new()` and then `setup(net, id)`.
- **The wave scene lives on through the upgrades:** players, weapons and items are still in the tree while RunData is the 1-player solo view. Anything they do then for players 1+ raises script errors. In a session `clean_up_room` clears every player weapon's target, disables its range (in the Boss mode the boss still stood there and the team kept attacking it) and stops its child timers (the rail gun's one-second timer calls `init_stats`, which read the gone player's effects), and `_lan_drop_stats_reloads` turns off item pickup and attraction (a Team Race player picked up a fruit in the solo view).
- **Boss digests:** the boss's HP bonus is a host-only `TempStats` change during the wave, and the digest includes max HP, so host and client digests taken mid-wave differ in Boss mode; the runs sent between waves match.
- **Filtering a vanilla area handler:** a weapon's `_on_Range_body_exited` disconnects the `died` signal its `_on_Range_body_entered` connected; when the entry is filtered out (`mode.can_target`), skip the exit only for bodies that were never connected, not for those no longer in `_targets_in_range` (a target that died is removed but stays connected; skipping its exit gave "already connected" errors when the pooled enemy came back).
- **GDScript 1:** `continue` inside `match` falls through to the next pattern; use `if`/`elif` in loops. Compare arrays by value with `==`. `sync` (like `master`, `puppet`, `remote`) is a keyword; don't name a variable after it.
- **Native methods can be overridden for script callers:** vanilla scripts calling e.g. `get_global_mouse_position()` reach an extension's method of that name (the engine itself doesn't); `.get_global_mouse_position()` calls the native one.
- **`WaveTimer.stop()` only pauses:** its `_physics_process` restarts the tick sound while 0.1–6 s are left, so a timer stopped early (a client's, which lags the host's) ticks on; `clean_up_room` turns its physics off in a session.
- **Per-wave state across runs:** a new run in the same session starts at wave 1 again, so state keyed only by the wave number (like `LanNet.wave_end_state`) must be cleared when a wave is entered, or the next run takes the old one for its own.
- **Coop-only UI setup:** vanilla UIs set themselves up in `_ready` only for the run type they were made for (`UpgradesUI._ready` returns when `RunData.is_coop_run != is_coop_ui`). In a session the solo `UpgradesUI` in `main.tscn` is therefore unset; it runs `_ready` again once the solo view is active.
- **Solo view hazards:** while it is active, `RunData` has one player, but `main` still has every player node. Anything that indexes players by their coop index must be off (`LanWaveSync.stop()`) or mapped (`main.on_gold_changed` / `on_xp_added` map index 0 to the local HUD). Never apply a run (`RunBuilder.apply_run`) inside the solo view: leave or discard it first.
- **Applying a run clears what isn't in the run state:** `RunData.reset()` resets `run_won`, `difficulty_unlocked` and per-wave values; keep what the current scene needs (7f).
- **Title screen:** vanilla `title_screen.gd` `_ready` calls `RunData.reset()`. Its child `Menus` (the extension) is ready before it, so `LanNet.on_title_screen()` runs first.
- **Yield on another object's signal from a scene:** if the scene is freed before the signal fires, the resumed function errors ("class instance is gone"). Relay it through a signal on the scene itself (`main.lan_wave_end_ready`).
- **Several connections to one signal** run in no guaranteed order; don't let them depend on each other.
- **Signals while a scene is freed:** a scene leaves the tree children first, and a focused control emits `focus_exited` on the way out. A handler that then fills vanilla UI (e.g. an item description, whose `EffectLine`s need `_ready`) on nodes already out of the tree raises script errors in vanilla files. Check `is_inside_tree()` of what it fills (the lobby previews, 8b).
- **Shop:** vanilla's Go button clears Go when it loses focus (`_on_GoButton_focus_exited`); the waiting overlay takes the focus. `_on_tree_exited` curses locked items randomly per player, so in a session only the host does it (`RunBuilder.apply_go`). The Go handler's hourglass, extra-elite roll and wave increment must run once for everyone (host).
- **Don't extend `overlap/hitbox.gd`:** its inner class `HitboxArgs` has methods typed `-> Hitbox.HitboxArgs`; the reload that installs an extension breaks them (`Parse Error: The returned value type (HitboxArgs) doesn't match the function return type (HitboxArgs)`). Change hitboxes from their owner's extension instead.
- **Vanilla `stop()` returns a projectile without stop delay to the pool at once** (enemy bullets), which clears `lan_net_id` in the extension's `_return_to_pool`. The `projectile.gd` extension takes id and position before calling it; otherwise hits on players were never reported and clients' bullet copies flew on.
- **`Utils.default_die_args` keeps the last killer:** vanilla's `Player.take_damage` writes the killer into it before `die()`, and nothing clears it, so a later `die()` without args can carry a freed `from`; `main._on_player_died` then raises "Left operand of 'is' was already freed" (attributed to the mod's `main.gd`). The session kills players with fresh args (`LanWaveSync._player_die_args`).
- **Save loader has 4 slots** for `locked_shop_items` and `shop_items` (`ProgressDataLoaderV3`); the extension handles the rest. Extending a `class_name` script works for `ClassName.new()` too.
- **`saved_run_state` changes in memory during a session** (shop, lost run) although disk saves are blocked; the `progress_data.gd` extension puts the own one aside.
- **Disconnects during a run** must not reset the run id (`_broadcast_lobby_state(run_in_progress)`), or a pending next-wave sync stalls; lobby entry changes are ignored during a run for the same reason.
- **Run JSON:** runs travel as JSON text through the save loader (`ProgressDataLoaderV3.new()` without args touches no disk). The deserializers expect JSON types (string keys, floats); raw RPC dictionaries make `PlayerRunData._deserialize_effects` raise script errors. JSON turns ints into floats; `RunBuilder.apply_run` fixes the known keys.
- **ENet** calls `close_connection()` itself right after `server_disconnected` / `connection_failed`; closing again logs an engine `ERROR:`. Cleanup runs deferred and the close is guarded by the connection status. Broadcast only to peers in `get_network_connected_peers()`.
- **Menus:** `MyMenuButton` re-enables itself after its 0.05 s press delay; use its `disable()` / `activate()`, not `disabled`. Every page's `_input` must `set_input_as_handled()` after `ui_cancel`, or the page that becomes visible handles the same event. `ui_cancel` closes an open `OptionButton` popup on press, so leaving a page needs press *and* release with no popup open.
- **Unique names:** copying a `%Name` node, rename it before setting `owner`; setting `owner` claims the unique name.
- **Inventory elements are `Button`s:** an empty one's minimum height is the theme font's plus the stylebox's (68 px with the page theme). Give the grid a theme with a smaller `Button` font to keep 56 × 56 tiles.
- **Delayed vanilla work across the solo view:** anything vanilla queues during the wave and runs later (`StatsManager` reloads up to 60 frames, timers, deferred calls) can run once `RunData` is the 1-player solo view, where indices 1+ don't exist. Drop or finish it before `enter_solo_view` (see `_lan_drop_stats_reloads`).
- **Test driver:** see [testing.md](testing.md#writing-steps).
